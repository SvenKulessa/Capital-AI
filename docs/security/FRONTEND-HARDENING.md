# Frontend security hardening — 2026-09-30

Scope: `SvenKulessa/Capital-AI`. This is implementation/evidence, not a new governance or deployment authority. Fresh owner direction authorizes this bounded hardening. SEC provides security constraints; FE implements the interface, OPS receives the runtime/configuration handover. No productive PVC ownership is transferred.

## Changes

- Telegram bot token and destination are runtime configuration only. Legacy browser preferences are reconstructed from an allowlist on load and write, dropping credentials/unknown keys and stale connection assertions. The browser sends plain text to a same-origin endpoint; the backend enforces the OIDC session, explicit subject authorization, fixed destination, origin, body size, timeout and rate limits. No simulated delivery is reported as successful.
- Fake password-login, registration and reset success messages are removed. A server-side OIDC Authorization Code flow uses S256 PKCE, random state, nonce, a browser-bound one-time transaction and signed ID-token validation. Issuer, audience, authorized party, nonce, expiry and issued-at are checked. Only opaque `__Host-` cookies reach the browser (`Secure`, `HttpOnly`, session `SameSite=Strict`; temporary callback cookie `SameSite=Lax`). Access/ID tokens are not stored in browser storage or returned by session endpoints.
- OIDC sessions last at most 30 minutes and no longer than ID-token expiry. Sessions/transactions are process-local, bounded and pruned. Restart or sleep loses sessions; there is no refresh or persistent-login promise. Logout invalidates the local session; it does not sign out from the identity provider. No OIDC claim establishes paid entitlement or domain authorization.
- Anonymous market reads remain public, with a process-wide 120/minute limit, eight concurrent requests, per-symbol single-flight and a five-second negative cache. Authentication is limited to 20 login/callback requests per minute per process. Telegram is limited to 30/minute globally and 5/minute per allowed subject. Forwarding headers do not identify trusted clients. Multi-instance operation needs a separately reviewed shared session/limiter implementation; the intended Render instance count is one.
- Pipeline persistence rejects invalid schema rows; local imports are bounded to 50 saved pipelines, 200 nodes and 400 edges per pipeline, 262144 JSON characters per import and 2 MiB-character storage budget. Invalid entries are discarded, storage failures return no false import success, and imported IDs use UUID v4. Schema-valid drafts remain editable; this does not grant scoring/execution eligibility.
- Gemini runtime code moved out of `src/` into a dev-only server handler. The browser only imports types and has no provider/credential fallback. Production continues to reject `/api/advisor`; it is not silently enabled as a billable service. The development endpoint is local, origin-limited, body/schema-limited and rate-limited. Provider error objects are not logged.
- CSP removes direct browser access to Telegram and server-owned market feeds. Inline analytics initialization is removed; initialization already exists in the client utility. Third-party analytics remains CSP-blocked pending an independently verified consent policy; script CSP is not weakened.

## OIDC owner configuration

Choose an HTTPS OIDC provider supporting discovery, S256 PKCE and `client_secret_basic` token authentication. No provider, account or Supabase project was connected by this change.

Configure runtime variables `PUBLIC_APP_ORIGIN`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`. `PUBLIC_APP_ORIGIN` must be an exact HTTPS origin without a path; `OIDC_ISSUER` must exactly match the discovery issuer. Register the single redirect URI `PUBLIC_APP_ORIGIN + /api/auth/callback`. Provider account creation, password recovery and MFA stay with the identity provider. Missing configuration fails closed with `authentication_not_configured`.

For Telegram set runtime-only `TELEGRAM_BOT_TOKEN`, numeric `TELEGRAM_CHAT_ID`, and `TELEGRAM_ALLOWED_SUBJECTS` (exact verified OIDC subject IDs for the configured issuer; comma-separated). Never prefix these variables with `VITE_`. Use the verified session endpoint to identify the subject after real provider login. Any previously browser-stored token should be revoked in BotFather before enabling the server-owned bot. Rotation and provider configuration remain owner actions; no credentials were collected or reused.
